# CXBA 以人员为中心的数据分析办案方法

## 1. 目的

本方法用于处理“举报某人报销异常、收受利益、利益输送”等混合案件材料。目标不是让模型直接判断违纪违法，而是形成一套可复跑、可回查、能反证、可交人工认定的调查底稿。

核心主线只有一条：

> 以身份和关系确定查谁，以职务和时间确定查什么，以资金和报销验证利益，以企业、设备和时空碰撞补强控制或接触，以反证排除正常解释，最后逐条交付证据 Claim。

## 2. 三类角色边界

### 2.1 办案人员

- 确定举报语义、对象、期间、职务权限和需证明的行为。
- 提供组织关系、审批权限、业务背景及模型无法取得的材料。
- 对身份冲突、业务合理性、利益性质和责任作最终认定。

### 2.2 大模型或小模型

- 拆解问题、选择 Skill、安排工具顺序、解释字段和组织证据。
- 主动寻找支持证据、反证、正常解释和材料缺口。
- 不凭印象算金额，不把高额、同名、同事、亲属、时间接近直接写成违规事实。

### 2.3 确定性工具和脚本

- 负责全量读取、金额计算、时间匹配、去重、来源对账和结果复算。
- 输出必须保留输入范围、字段、口径、排除规则和原始定位。
- 计算错误必须暴露，禁止静默跳过文件、Sheet、页或异常行。

## 3. 输入合同

开始前先把用户问题改写成以下结构。未知项写“未知”，不能自行补造。

```yaml
subject: 目标人员
allegations:
  - 费用报销是否存在虚假、重复、拆分或利益代付
  - 是否接收下属、客户、关联企业或其他利益相关方利益
period: 待查期间
subject_roles: 已知职务和权限，未知则待补
material_scope: 本次授权材料根目录
calculation_scope:
  currency: 分币种统计
  direction: 从目标账户或目标主体视角定义流入流出
  duplicate_rule: 只有证据证明同一业务记录时才合并
required_output:
  - 客观事实
  - 可复算统计
  - 时序关联候选
  - 业务推断或疑点
  - 反证和正常解释
  - 材料缺口和补证清单
```

如果对象、期间、方向或“全部”的含义会改变结果，应先询问；不影响只读盘点和结构理解的未知项先登记后继续。

## 4. 总体执行顺序

### 阶段 0：建立只读边界

- 原始材料只读挂载到 `/data`。
- 脚本、底稿和结果只写 `/workspace`。
- 不联网，不上传案件内容，不安装运行时依赖，不修改原件。
- 对原始文件记录路径、真实格式和大小；疑似重复文件使用逐字节比较确认，不新增业务哈希、数据哈希或审批门禁。

输出：`investigation-state.md`，写明范围、对象、问题、未知项、当前步骤和下一步。

### 阶段 1：建立全材料覆盖台账

对材料根目录生成薄清单，但薄清单只防遗漏，不是证据。

每个文件必须有一个状态：

- `STRUCTURE_CHECKED`：真实格式和结构已确认。
- `FULLY_SCANNED_BY_SCRIPT`：已由确定性脚本全量扫描。
- `RELEVANT_ORIGINAL_VERIFIED`：目标命中已回查原件。
- `EXACT_DUPLICATE`：与另一文件逐字节完全相同。
- `EMPTY`：经结构和渲染复核后确认无正文或数据。
- `ENCRYPTED`：只能看到容器或成员信息，内容未解密。
- `PARSER_GAP`：当前解析器无法完整读取。
- `OUT_OF_SCOPE`：有明确理由证明与当前问题无关。

“没有遗漏”不是声称所有内容都已被模型放进上下文，而是：所有文件都有处理状态，所有大表都经过全量确定性扫描，所有重要命中都回到原件核实，所有失败和未读范围都被列为缺口。

### 阶段 2：识别来源关系

先分清每份材料是什么，再计算：

- 原始明细、加工明细、汇总表、截图、查询回执、关系证明或附件副本。
- 同一来源的重复导出、不同来源的独立证明、一个来源包含另一个来源、互相补充或存在冲突。
- 只有逐字节完全相同的文件才能标记文件级重复。
- 只有稳定业务键相同且关键字段一致的记录才能自动合并。
- 汇总表只用于核对明细，不与明细再次相加。

输出：`source-register.json` 和必要的来源对账结果。

### 阶段 3：建立目标人员身份和职务时间轴

先证明“这个人是谁、何时处于什么岗位、能影响什么”，再查钱。

至少核对：

- 强身份标识：人员号、完整证件标识、客户号、完整账户 ID、明确原始关系材料。
- 姓名、别名、曾用名和同名冲突。
- 任职单位、部门、岗位、起止日期、审批或业务权限。
- 上下级、同部门、亲属、客户和业务合作方关系及其来源。

姓名相同只能生成身份候选。人员只按强标识归并；账户按账户类型和完整账户 ID 归并。

输出：`subject-profile.md`、`role-timeline.json`、`identity-map.json`。

### 阶段 4：建立问题队列

同一时间最多推进三个主线问题。每个问题必须同时写四项：

1. 支持假设。
2. 正常解释。
3. 反向假设。
4. 需要的证据和当前缺口。

例如“下属向目标人员转款是否构成利益输送”不能只查转账，还要查：

- 是否为借款、代付、投资、归还、家庭或共同消费。
- 是否存在返还、反向流水、对应合同、聊天、审批或业务事件。
- 转款前后目标人员是否实施了可影响对方利益的职务行为。

### 阶段 5：人员中心的九条调查线

#### 5.1 身份与关系线

- 从目标人员出发建立一跳关系：亲属、上下级、同部门、业务客户、企业股东高管、经办审批人。
- 每条边记录“关系类型、开始结束时间、来源、稳定标识、是否仅为候选”。
- 只有出现资金、审批、报销对象、业务事件、设备或时空等桥接事实时，才从背景关系升级为待核关联。

#### 5.2 职务与业务权限线

- 把任职时间和举报期间对齐。
- 明确目标人员是否能审批、推荐、授信、营销、采购、分配资源或影响业务。
- 把可能受益方的业务事件放到同一时间轴。
- 没有职务影响或事项发生在任职期外，必须作为反证或限制。

#### 5.3 个人资金线

- 枚举目标人员全部已确认账户，不能只分析一张卡或一个银行。
- 从目标账户视角统一定义流入、流出、自转和未知对手。
- 分币种统计总额、笔数、净额、峰值、频次和期间分布。
- 识别大额集中、整数金额、周期性、下属或客户流入、短时再投资、回流、汇聚和多跳候选。
- 时间接近和金额相似只能生成候选，不能直接认定为同一笔资金。

#### 5.4 费用报销线

- 先确认申请人、经办人、收款人、付款人、审批人和实际支付对象字段。
- 按人员、期间、费用类别、商户、金额、审批链和支付状态全量计算。
- 检查集中度、突然增长、重复金额、拆分、阈值附近、非工作时段、相同票据或商户、退款冲正。
- 报销台账只能证明报销记录，不能单独证明业务虚假或个人收受利益。
- 要形成闭环，还需合同、发票、行程、付款、实际服务、审批权限和受益人的相互验证。

#### 5.5 企业与业务往来线

- 查企业股东、高管、经办人、联系电话、地址、账户、客户号和业务流水。
- 将目标人员任职权限与企业获得业务、额度、交易、费用或其他利益的时间对齐。
- 企业交易规模大、与同一银行往来或名称频繁出现，本身不等于目标人员收受利益。

#### 5.6 账户、设备和联系方式控制线

- 比较完整账户 ID、客户号、手机号、邮箱、地址、登录设备、IP、经办柜员等标识。
- 共享手机号、地址、设备或 IP 可支持“可能共同控制或共同经办”，但要排除办公室网络、代理记账、家庭共用和银行批量维护等正常情形。
- 文件名中出现的号码或关系只用于定位，必须由正文、系统记录或其他原件确认。

#### 5.7 时空与行为碰撞线

- 先把交易规范化成统一事件，再观察时间精度和分布，选择多个分析窗口。
- 查同日、短时先后、夜间集中、多人汇入后转出、快进快出、回转和多跳链。
- 每个候选写明窗口、方向、币种、金额差、保留比例、其他合理候选和未匹配余额。
- 时间相邻只属于 `TEMPORAL_ASSOCIATION`，不能自动证明因果或资金同一性。

#### 5.8 资产和最终利益线

- 查资金最终进入存款、理财、证券、房产、车辆、消费、家庭成员或关联企业的路径。
- 区分本金、收益、分红、退款、归还和账户内部划转。
- 只有“利益来源—目标控制—最终受益—职务事项”关键跳均有证据时，才形成较强候选链。

#### 5.9 反证和缺口线

每发现一个支持点，必须同步检查：

- 反向流水、返还、退款、冲正、撤销和余额不足。
- 借款、投资、代付、共同消费、家庭往来、内部划转等替代解释。
- 同名、身份未解析、时间不一致、币种不同、方向错误。
- 来源重复、汇总与明细重复累计、材料期间不完整。
- 缺少合同、发票、审批、聊天、业务事项、账户控制或外部银行材料。

### 阶段 6：做两轮实体扩展扫描

第一轮以目标人员的姓名、别名、强标识、账户和任职单位扫描全部可解析材料，只把命中用于定位。

第二轮使用第一轮从原件确认的新标识继续扫描：

- 关系人强标识和账户。
- 企业名称、客户号和账户。
- 手机、地址、设备、IP、经办人和审批人。
- 关键日期、金额和业务编号。

至少完成两轮。第二轮仍出现新强标识时继续扩展；连续一轮没有新增强标识或新文件命中，并且覆盖台账无未处理文件，才可以停止扩展。姓名和近似金额命中不能直接创建身份或交易关系。

### 阶段 7：跨来源碰撞

优先做能回答案件问题的碰撞，不做无边界的全量关联：

- 人员关系 × 资金往来。
- 职务期间 × 企业业务事件。
- 报销记录 × 付款流水 × 发票或服务。
- 资金流入 × 短时投资或资产形成。
- 企业控制标识 × 账户、设备、地址和经办人。
- 业务受益 × 目标人员或关系人最终受益。

每一跳都要写明主体、角色、方向、时间、金额、关联键、容差和原始定位。任一关键跳不成立，整条链不得写成已证实。

### 阶段 8：形成证据 Claim

把报告拆成最小可验证陈述，事实和推断不得混在一条里。

- `FACT`：原件直接记载的字段、记录或明确关系。
- `CALCULATION`：可由脚本复算的合计、笔数、比例、净额或排名。
- `TEMPORAL_ASSOCIATION`：时间相邻、同窗或先后关系。
- `BUSINESS_INFERENCE`：基于事实形成的解释或待核疑点。
- `HYPOTHESIS`：尚无充分原始证据的调查假设。
- `GAP`：材料缺失、解析失败、身份冲突或需要人工判断。

建议的最小结构：

```json
{
  "claimCode": "C-001",
  "claimType": "FACT|CALCULATION|TEMPORAL_ASSOCIATION|BUSINESS_INFERENCE|HYPOTHESIS|GAP",
  "statement": "最小可验证陈述",
  "scope": {
    "subject": "目标人员或账户",
    "period": "起止时间",
    "direction": "流入|流出|自转|不适用",
    "currency": "币种",
    "deduplication": "去重规则"
  },
  "sourceRefs": [
    {
      "sourceFile": "原始文件相对路径",
      "sourceSheetOrPage": "Sheet、页码或段落",
      "rowsOrCells": ["不连续记录逐条列出"]
    }
  ],
  "calculationRef": "脚本和结果路径，若适用",
  "supportingFacts": [],
  "opposingFacts": [],
  "alternativeExplanations": [],
  "limitations": [],
  "requiredMaterials": [],
  "humanDecisionRequired": true
}
```

### 阶段 9：独立复核和人工认定

- 复核方不继承调查模型的推理，直接重跑脚本并回查原件。
- 关键金额先重跑原脚本，再用独立方法从原件复算。
- 每条 Claim 只能判为 `PASS`、`RETURN_FOR_CORRECTION` 或 `NEEDS_HUMAN`。
- 有未解决身份、来源、业务含义或外部补证问题时，必须保留 `NEEDS_HUMAN`。
- 模型最终只能给“已证实事实、较强候选、一般线索、未证实、缺口”，不能作违纪违法终局认定。

## 5. Skill 调用路由

所有任务先加载`cxba-analysis-router`，由它识别任务类型；Router只选路，不读材料、不做事实判断。选定分支后只加载本轮需要的专项Skill，避免把一个简单问题拖进完整案件流程。

无论走哪个分支，都加载两个公共底座：

- `cxba-analysis-notebook`：每处理完一个实际文件，必须在下一次内容工具前记录主要内容、实际覆盖、可能用途、可疑线索或反证、精确原始定位和限制。
- `cxba-claim-delivery`：最终回答中的事实、计算、关系、候选或缺口均写成可回查Claim，并绑定真实`materialId`、完整相对路径、Sheet/页/原始行及计算脚本和结果。

新增单项技战法时，通常只需新增一个边界清楚的专项Skill，并在Router增加一个识别分支；公共Notebook和Claim合同由新Skill直接复用，不在每个技战法中复制一套。完整案件调查、独立复核和材料结构盘点仍保留独立分支。

| 场景 | 首选 Skill | 作用 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 用户要求完整案件调查 | `cxba-case-investigation`、`cxba-case-investigator` | 建立状态、问题队列、底稿和总报告 | 范围与材料台账已建立 |
| 材料范围不清楚 | `cxba-material-profiling` | 建薄清单、识别真实格式和覆盖范围 | 相关文件和结构已确认 |
| 混合、不规则原始材料 | `cxba-raw-material-investigation` | 统一证据方法、全量计算和原件回查 | 字段角色和计算口径明确 |
| Excel、XLS、CSV、TSV | `cxba-safe-tabular-analysis` | 安全读取全部 Sheet、确认表头和精确计算 | 关键命中已取得原始定位 |
| 明确文件、人员或指标的追问 | `cxba-interactive-data-analysis` | 做有界、定向计算或解释 | 回答已引用原始位置 |
| 报销、费用或审批规律 | `cxba-expense-pattern-analysis` | 分析集中度、突增、重复、拆分、阈值和冲正 | 候选已回查支付和业务材料 |
| 多来源可能重叠或冲突 | `cxba-source-reconciliation` | 识别重复、包含、补充和冲突 | 安全合并结果与未解决冲突已分开 |
| 快进快出、汇聚、回转、多跳 | `cxba-temporal-graph-analysis` | 规范化事件并做有界时序图搜索 | 标准脚本成功且候选已回查原行 |
| 报告和证据包完成 | `cxba-evidence-review` | 独立复算、逐 Claim 审查 | 所有可修正项处理或明确交人工 |

Skill 是流程和判断约束，不替代原件读取与确定性计算。若 Skill 或依赖失败，记录真实错误和未完成范围，禁止换一个近似字段继续算。

## 6. 文件类型处理矩阵

| 文件类型 | 必做检查 | 全量处理方式 | 常见漏点 |
| --- | --- | --- | --- |
| `.xlsx` | 所有 Sheet、真实表头、合并区域、公式、隐藏行列、实际数据范围 | `openpyxl`、`pandas` 或 DuckDB；金额用十进制定点 | 只读第一个 Sheet、公式值缺失、稀疏表虚高行数、无效筛选范围 |
| `.xls` | 先确认是旧版 Excel 真实格式 | 优先用预装 `xlrd`；不支持时在工作区临时转为 `.xlsx`，保留源路径、转换映射和原件不变 | 转换失败被当无数据、中文路径导致批量转换漏件 |
| `.csv/.tsv` | 编码、分隔符、引号、换行、前导零 | 流式读取并记录编码；常见中文材料尝试 UTF-8、GB18030 等 | 账户和证件被转成科学计数、方向字段误解 |
| `.docx` | 正文、表格、页眉页脚、内嵌图片 | 文本和表格抽取后必须渲染页面；图片型页面再 OCR | 文本抽取为空但页面实际有整页图片 |
| `.doc/.rtf` | 真实格式、正文、表格和内嵌对象 | 在工作区临时转 PDF 或 DOCX，渲染核对；RTF 同时做文本抽取 | 旧格式解析器只返回少量字符串 |
| `.pdf` | 页数、是否扫描件、文字层、旋转和清晰度 | 先抽取文本，再逐页渲染；扫描页 OCR 后回看原图 | OCR 错把账号、日期、金额或姓名识别错误 |
| `.msg` | 发件人、收件人、时间、主题、正文、附件名和附件内容 | 使用预装邮件解析器；附件单独登记，疑似外部副本逐字节比较 | 只看到附件名、正文未解析却声称全文已读 |
| `.zip/.7z` | 成员清单、路径、大小、加密状态 | 只在工作区解压；加密无密码时记录 `ENCRYPTED` | 外部同名文件未做字节验证却当作同一附件 |
| 图片 | 分辨率、方向、页序、可读区域 | OCR 只做定位，关键字段人工或视觉回查 | OCR 数字混淆、裁剪掉印章或表头 |
| 空白、损坏或未知格式 | 文件签名、大小、渲染和替代解析器结果 | 保留原错误并登记状态 | 把解析失败写成“无记录” |

转换件、OCR 文本和规范化 JSONL 都是分析副本，不是原始证据。报告引用必须回到原文件、Sheet、页码、行号或单元格。

## 7. 工具使用顺序

### 7.1 结构和完整性

- `terminal`：目录枚举、真实格式、逐字节副本比较、压缩包成员和可复跑脚本。
- `file`：有界读取原文、关键行和结果片段。
- Office/PDF 渲染工具：将图片型 Word、旧版 Word 和 PDF 渲染为页面。
- OCR：只做发现和定位，关键字段回看页面。

### 7.2 确定性分析

- Python、`pandas`、`openpyxl`：表格结构、筛选、聚合和精确定位。
- DuckDB：跨大文件重复查询、临时规范化和有界图分析。
- `execute_code`：短探索可以临时运行；正式结论必须沉淀为 `/workspace/scripts` 可复跑脚本。
- 时间图分析统一读取 `events.jsonl`，不能同时维护两套互相冲突的事件集。

### 7.3 可信业务数据

- 需要案件成员、权限、全局主档或审批信息时，只调用 Spring 提供的可信 MCP 工具。
- 模型输入的 `caseId`、`userId` 或 Session 标识不能作为权限依据。
- 不向 Sandbox 下发数据库凭据，不由模型拼接任意数据库 SQL。

## 8. 小模型执行规约

小模型上下文有限，必须把进度、规则和结果放在文件中，而不是依赖长对话记忆。

### 8.1 每次只完成一个清晰动作

推荐循环：

1. 读取 `investigation-state.md`。
2. 读取当前阶段一个 Skill。
3. 执行一个可验证动作。
4. 检查退出状态和产物。
5. 把覆盖、结果、错误和下一步写回状态文件。
6. 需要形成 Claim 时回查原件，再进入下一动作。

### 8.2 对话只放有界信息

- 大表、全文、OCR 全量结果和图路径留在工作区。
- 对话只读取结构摘要、有限样本、Top 候选和当前 Claim 需要的原始行。
- 所有详细输出使用明确的 `top`、`sample` 或上限。
- 截断输出不能作为证据，也不能据此声称没有其他候选。

### 8.3 固定工作区结构

```text
/workspace/
  investigation-state.md
  thin-inventory.json
  source-register.json
  material-notes/
  scripts/
  results/
  evidence-items/
  draft-report.md
  case-investigation-report.md
```

### 8.4 失败时停止升级结论

以下情况不得继续强化表述：

- 文件、Sheet、页或附件未解析。
- 身份只能靠同名匹配。
- 金额方向、币种、单位或去重口径不明。
- 关键计算不能重跑。
- 引用不能回到原始位置。
- 链条关键一跳缺证。
- 只有时间接近、金额近似、关系背景或算法命中。

应输出 `GAP`、修正任务或补证问题，不允许用“高度疑似”掩盖缺口。

## 9. 报告结构

最终报告按以下顺序，先事实后判断：

1. 调查问题、对象、期间和口径。
2. 材料覆盖：文件、Sheet、页、解析失败、加密件和完全重复件。
3. 已证实的身份、关系、职务和账户事实。
4. 可复算的资金、报销、企业和资产统计。
5. 已回查的时序或跨来源关联候选。
6. 每条候选的支持证据、反证、替代解释和关键缺口。
7. 已排除事项及排除依据。
8. 待补材料和建议询问事项。
9. 逐条 Claim 及原始定位。
10. 独立复核结果和人工认定事项。

结论用语建议：

- “原始材料直接记载……”
- “全量脚本计算显示……”
- “在所声明窗口内形成时序关联候选……”
- “现有材料不足以证明……”
- “存在以下正常解释，需补充……排除。”
- “该事项需要办案人员结合……作人工认定。”

禁止用语：

- “肯定收受利益”“已经实锤”“必然是同一笔钱”，除非每个法律和事实要件已有相应原始证据并经有权人员认定。
- “未发现所以不存在”，除非材料范围、字段、期间、身份和解析覆盖均足以支持不存在结论。

## 10. 完成检查清单

只有以下项目全部完成，才能说本轮数据分析闭环：

- [ ] 用户问题已拆成对象、行为、期间、方向、币种和统计口径。
- [ ] 所有文件都有覆盖状态，隐藏文件和重复件已登记。
- [ ] 所有 Excel/CSV 的相关 Sheet 和全量数据已由脚本扫描。
- [ ] 文本抽取近乎为空的 Word/PDF 已渲染复核。
- [ ] 邮件正文、附件和加密压缩包的未读范围已明确。
- [ ] 目标人员身份和全部已确认账户按强标识归并。
- [ ] 职务时间轴、上下级和业务权限已核对。
- [ ] 资金、报销、企业、设备、时空和资产线均已检查或说明不适用。
- [ ] 已完成至少两轮实体扩展扫描。
- [ ] 汇总、明细、重复导出和独立来源未重复累计。
- [ ] 正式金额、笔数、排名和时间匹配均可复跑。
- [ ] 每个关键数字和候选都能回到原文件位置。
- [ ] 每个支持点都检查了反证和替代解释。
- [ ] 报告已拆成最小 Claim，事实、计算、时序和推断分开。
- [ ] 关键金额已独立复算，非 `PASS` 项已修正或交人工。
- [ ] 授权办案产物中的身份、账号等原始标识与原件一致，未因掩码造成主体或方向无法核验；生产日志和非办案展示未带出案件原值。

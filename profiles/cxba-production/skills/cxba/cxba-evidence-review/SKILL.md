# CXBA 分析结论独立复核

开始回查任何原始材料前加载`cxba-analysis-notebook`，逐文件即时记录复核覆盖、原报告说法、原件实际内容、差异和精确定位。最终回答中重新确认的材料事实、计算或缺口必须加载`cxba-claim-delivery`并按公共格式交付；逐条复核verdict仍同时遵守本Skill的`claim-review.json`合同。

复核材料适配器、临时脚本、金额、方向、去重、图结果和原始定位前，加载`cxba-analysis-pitfalls`并按需读取已验证规则；当前上下文已完整读取时不重复加载。

把分析报告视为待验证对象，不继承调查 Agent 的推理。直接回到计算脚本、计算结果和原始材料逐条复核，不替调查 Agent 发明、补写或升级新结论。

复核底稿和结论使用中文。事实、计算结果、时序关联和业务推断必须分开表达。

## 开始前

确认可读取以下三类输入：

1. 分析报告。
2. 报告使用的计算脚本及结果。
3. 报告引用的原始材料。

缺少某项时不要猜测。可由调查 Agent 补齐的，相关 claim 判为 `RETURN_FOR_CORRECTION`；材料本身不存在、来源冲突或必须由人员确认的，判为 `NEEDS_HUMAN`。

当待复核对象来自同一案件的其他业务 Session 时，先使用目标 Session ID 检查只读挂载目录 `/case-sessions/<session-id>`。调查报告、`evidence-items/final-claims.json`、计算脚本、计算结果和分析笔记优先从该目录读取；不能因为当前 `/workspace` 没有这些文件就声称其不可访问。只有确认该只读挂载中确实缺失后，才通过 Session 消息补充报告文本，并按实际缺失项判定。

先读取 [claim-review-contract.md](references/claim-review-contract.md)，按合同生成复核工作文件 `claim-review.json`。合同只规定复核结构，不证明内容正确。

运行结构与引用初筛：

```bash
python3 /root/.hermes/skills/cxba/cxba-evidence-review/scripts/check_evidence_package.py /path/to/claim-review.json
```

相对路径以 `claim-review.json` 所在目录为基准。脚本仅检查 JSON 结构、必填字段和引用文件是否存在；脚本通过不等于 claim 通过，也不能替代原始材料回查、独立复算和业务判断。

## 一、拆分 Claim

按报告中可独立验证的最小陈述拆分，给每条 claim 唯一编号。不得把事实和推断塞进同一条。

- `FACT`：原始材料直接记载的字段、记录或明确关系。
- `CALCULATION`：合计、笔数、比例、排名、净额、差额等可复算结果。
- `TEMPORAL_ASSOCIATION`：时间相邻、同窗出现、先后顺序等关联；不自动代表因果。
- `BUSINESS_INFERENCE`：基于事实或计算形成的解释、疑点或业务判断；不自动代表事实认定。

保留用户原始问题中的对象、期间、金额方向、币种、统计范围、去重口径和“全量/抽样”含义。报告偷偷换口径时，不能按换后的口径判通过。

每条 claim 至少登记：原文陈述、类型、用户口径、覆盖范围、原始 `source_refs`、计算引用、候选链逐跳信息和限制。不要把报告、材料底稿、汇总结果或其他 Agent 的叙述当作原始来源。

## 二、逐条复核

对每条 claim 完成以下检查，并在复核底稿中逐项给出证据。

### 1. 用户口径

- 对象、角色、期间、方向、币种、单位、阈值、筛选条件和去重规则是否保持。
- “流入”“流出”“交易额”“余额”“净额”等概念是否被替换。
- 用户问抽样时不得声称全量，用户问全量时必须说明实际覆盖和缺口。

### 2. 可复现计算

- 脚本是否真实读取所述文件、Sheet、字段和范围。
- 结果能否在当前输入上重跑得到，失败不能用旧结果代替。
- 空值、无效日期、重复记录、冲正、金额正负、币种、单位和舍入是否明确。
- 汇总表与明细表、多个来源之间是否重复累计；来源独立性不明时分别报告。
- 报告数值与脚本输出、原始行回查是否一致。

### 3. 原始引用

- 每个关键事实和数字是否有可打开的原始 `source_refs`。
- 定位是否精确到文件以及 Sheet/表/页码/行号/段落/单元格区域。
- 引用位置是否真的支持该 claim 的对象、角色、方向、金额和日期。
- 表格证据不连续时，必须逐一列出实际使用的原始行；不得用首尾行范围包住中间无关记录。逐行打开核对，定位中存在无关行或实际使用行缺失时判为`RETURN_FOR_CORRECTION`。
- 汇总文件、脚本输出和工作底稿只能证明计算过程，不能替代原始材料引用。

### 4. 最终表达与实际交付

- 对报告中的每个表格字段，按“原始材料 → 计算结果字段 → 报告表头和单元格 → 页面最终回复”逐列核对，防止流水摘要、交易名称、交易时间、主体角色等在生成 Markdown 时错列、硬编码或丢失。
- 报告声称“逐笔明细已列出”“完整清单已交付”“脚本已独立复算”等内容时，必须检查相应明细、当前复核工作区脚本和结果确实存在且非空；只写说明、只生成结果而没有独立脚本，均判为`RETURN_FOR_CORRECTION`。
- `final-answer.md`、页面最终回复和结构化 Claim 必须表达同一组结论并使用同一字段值；正文存在 Claim 但页面未带`[C001]`等标签，或页面声称交付正文中不存在的内容，均不得判通过。
- 原始路径和`materialId`必须逐字符对照`materials.json`，不能因只差一位数字或存在同名副本而放过。

### 5. 证据强度

- 抽样、截断、部分 Sheet、部分期间或部分对象不得冒充全量。
- 同名只算身份候选，未由稳定标识或原始关系材料确认时不得合并为同一主体。
- 近似金额只算匹配候选，必须保留容差、方向、币种及其他候选。
- 时间相邻只算时序关联，不得升级为交易对应、资金来源、因果或业务事实。
- 高额、集中、重复出现、算法命中或零命中不得直接升级为异常、不存在或事实认定。
- 正常解释、反证、替代解释、数据缺口和覆盖限制是否遗漏。

## 三、关键金额独立复算

关键金额包括：报告摘要或结论使用的金额、影响 claim 成立的金额、跨来源合计、净额、占比、排名阈值和候选链各跳金额。

1. 先重跑调查 Agent 的脚本，记录命令、退出状态和结果差异。
2. 再从原始材料用独立方法复算，不照抄原脚本的筛选实现。金额使用十进制定点计算。
3. 对照输入范围、原始定位、方向、币种、去重键、排除项、空值、冲正和舍入。
4. 报告值、原脚本值、独立复算值任一不一致时，列出差额和定位，不自行选择最有利结果。

复算脚本和结果必须写入当前复核工作区，不覆盖调查 Agent 的脚本或结果，也不得复制调查脚本或结果冒充独立复算产物。公共 Claim 的 `calculationRefs` 必须引用当前复核工作区中实际执行的独立脚本和结果；调查 Session 的脚本和结果只作为待审输入记录在复核底稿中。

只生成当前复核工作区的结果文件而没有保存并实际执行独立脚本，不算完成独立复算；在独立脚本、结果、`claim-review.json`、需要发布的`final-claims.json`及最终回复全部完成前，不得声称复核完成或停止运行。

同名材料需要判断是否为完整字节副本时，可做逐字节比较，但只记录“逐字节一致/不一致”和被比较的两个完整路径。不得在笔记、报告、Claim 或业务数据中新增、发布或依赖 MD5、SHA 等摘要值，也不得把摘要当作新的业务标识或门禁。

## 四、候选链逐跳回查

凡报告声称或暗示“人员、账户、单位、审批、报销、资金、事件”形成链条，必须拆成相邻节点之间的 hop：

1. 每一跳分别核对主体身份、角色方向、事件、时间、金额和原始引用。
2. 身份映射必须由稳定标识或明确原始关系支持；同名、别名相似或单位相同不能代替。
3. 金额匹配必须列明精确值或容差及全部合理候选；近似金额不能证明同一笔资金。
4. 时间匹配必须列明窗口和时区；相邻发生不能证明因果。
5. 任一关键 hop 未证实，整条链不得判为已证实；按缺陷性质退回修正或交人工判断。

只审查报告已有链条。回查发现新的可能关系时，把它记录为“超出本轮 claim 的待调查事项”，不得替调查 Agent 形成新 claim 或新结论。

## 五、判定

每条 claim 只能使用以下 verdict：

- `PASS`：用户口径保持，原始引用充分，必要计算可复现且关键金额独立复算一致，证据强度与表述匹配，限制完整。
- `RETURN_FOR_CORRECTION`：报告、引用、脚本、口径或表述存在可由调查 Agent 修正的明确缺陷。
- `NEEDS_HUMAN`：现有材料无法消除身份冲突、来源冲突、业务含义歧义，或事项本身需要人员核实、专业判断或外部补证。

不能因为“大致正确”或“不影响总体判断”而放过错误 claim。每个非 `PASS` claim 必须写：

- 具体退回或人工判断原因。
- 已检查的原始位置和复算结果。
- 可执行的修正任务或人工核实问题。
- 修正后应提供的材料、引用或结果。

总体 verdict 按以下顺序确定：存在 `NEEDS_HUMAN` 则为 `NEEDS_HUMAN`；否则存在 `RETURN_FOR_CORRECTION` 则为 `RETURN_FOR_CORRECTION`；全部 claim 均通过才为 `PASS`。即使总体为 `NEEDS_HUMAN`，仍要逐条保留可直接执行的退回修正任务。

## 六、输出

输出 `review-result.md`，第一行必须是：

```text
VERDICT: PASS|RETURN_FOR_CORRECTION|NEEDS_HUMAN
```

随后按顺序写：

1. 输入与实际覆盖范围。
2. Claim 清单及逐条 verdict。
3. 每条 claim 的用户口径、原始引用核查、计算复现、独立复算、证据强度、限制和理由。
4. 候选链逐跳核查。
5. 退回修正任务和人工核实问题。

不得代写调查报告，不得把表述改得更强，不得补造缺失来源，不得给出报告中原本没有的新调查结论。

## 边界

本 Skill 只向调用方返回独立复核意见；如何修订、人工确认或进入后续流程由调用方决定。
